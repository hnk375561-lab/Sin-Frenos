# QA Phase 4 — Sin Frenos

## Alcance

Esta fase se enfocó en correcciones de robustez móvil y estados de interacción sobre las superficies modificadas en las fases anteriores. No se reabrieron decisiones visuales aprobadas, no se modificaron rutas, sitemap, catálogo técnico, moderación, detección de duplicados ni rate limiting.

## Correcciones aplicadas

Se corrigió el ciclo de vida del menú móvil del header. El efecto que cerraba el menú ya no depende del estado `menuOpen`, por lo que abrirlo no provoca un cierre inmediato en el mismo render. El CTA de publicación también permanece visible en el header estrecho y conserva el CTA completo dentro del menú móvil.

La autenticación ahora evita las burbujas de validación nativas del navegador mediante `noValidate` y muestra un mensaje diseñado para emails inválidos. Se mantiene el flujo magic link y `flowType: 'implicit'` sin cambios.

El composer de mensajes y el formulario de contacto del vendedor pasan a disposición vertical en teléfonos, evitando que el input y el botón se compriman o generen overflow horizontal. La bandeja conserva estados de carga, vacío, error y confirmación de envío.

El paso de fotos comunica un límite explícito de diez imágenes, rechaza el excedente con un mensaje visible y revoca los object URLs de las fotos rechazadas para evitar consumo innecesario de memoria en móviles. Se conserva la validación de tipo, tamaño, portada y reordenamiento.

## QA manual pendiente en dispositivos reales

No es posible confirmar desde este entorno el comportamiento de un selector de archivos real en Safari iOS o Chrome Android, incluyendo permisos de cámara, selección múltiple, orientación EXIF, compresión del navegador y límites de memoria. El propietario debe probar específicamente el paso de fotos con cero imágenes, una imagen, diez imágenes y un intento de cargar una imagen número once.

Tampoco es posible verificar aquí el teclado móvil real en `/mensajes`, especialmente si el viewport cambia al enfocar el input en Safari iOS. La implementación evita el overflow horizontal y usa un composer apilado en móvil, pero debe verificarse en un iPhone y un Android físico.

No se pudo validar el envío real de emails transaccionales porque no existen plantillas ni un proveedor de correo editable dentro de este repositorio. El flujo depende de Supabase y debe probarse desde el proyecto configurado, incluyendo apertura del magic link en otro navegador o dispositivo.

La lista de verificación final recomendada antes de publicar es probar anchos de 360 px, 390 px, 414 px y 768 px en Chrome Android y Safari iOS; completar el magic link; recorrer los ocho pasos de `/publicar`; probar el límite de fotos; abrir una conversación; enviar un mensaje; guardar y quitar favoritos; y abrir una publicación sin fotos.
