# Fase 5 — Indexabilidad y SEO real del marketplace

## Part 1: corrección técnica de indexabilidad

La ruta anterior `/listings/ver?id=...` era completamente client-side y no podía producir HTML estático por publicación, porque el parámetro `id` vivía en la query string. Se agregó la ruta canónica `/listings/{id}` con `generateStaticParams`, que consulta durante el build únicamente publicaciones con `status = 'published'` y excluye las filas marcadas como `metadata.source = 'seed-fase3'`. Los enlaces internos principales ahora apuntan a esta ruta estática; la ruta vieja queda disponible para compatibilidad con enlaces existentes.

Cada listing estático incluye en el HTML visible el título, precio, descripción, atributos principales y fotos. También incluye canonical, `og:title`, `og:description`, `og:image`, `og:url`, Twitter Card y JSON-LD de tipo `Vehicle` con `Offer`, precio cuando existe, moneda, condición usada, disponibilidad, kilometraje, marca y modelo.

El sitemap ahora agrega `/listings/{id}` para el mismo conjunto de publicaciones que se genera estáticamente. Esto evita anunciar URLs que no fueron generadas o que pertenecen a fixtures de prueba. La cadencia diaria existente en `.github/workflows/rebuild-cron.yml` dispara el workflow de deploy y, por lo tanto, vuelve a ejecutar el build con el inventario actualizado. El tradeoff aceptado es explícito: una publicación nueva, editada, vendida o removida se refleja en SEO en el siguiente rebuild diario, no en tiempo real. Las superficies dinámicas de contacto, favoritos y mensajes siguen siendo client-side.

Cuando el build no tiene acceso a las variables públicas de Supabase, `output: 'export'` no permite que una ruta dinámica devuelva cero parámetros. Para no inventar inventario, el código genera una única ruta técnica `__no-listings-at-build__`, con contenido explícito y metadata `noindex, nofollow`; no se agrega al sitemap ni se presenta como una publicación real. En GitHub Actions, el workflow ya expone `NEXT_PUBLIC_SUPABASE_URL` y `NEXT_PUBLIC_SUPABASE_ANON_KEY`, por lo que el build de producción debe generar los IDs reales disponibles en Supabase.

## Part 2: estrategia y contenido

Se agregó `/guias/vender-auto-usado-argentina`, una guía práctica y honesta sobre documentación, precio, fotos, descripción y contacto seguro. No afirma inventario, volumen de usuarios, ventas ni autoridad que el sitio no tenga. Incluye enlaces al catálogo técnico, al marketplace y a la publicación gratuita del vehículo. La guía usa JSON-LD de tipo `Article`, canonical y metadata Open Graph.

La estrategia prioriza búsquedas de intención transaccional y local, como vender un auto usado en Argentina, documentación para transferir, contacto directo y publicación sin intermediarios. La guía evita costos o requisitos jurisdiccionales específicos que podrían quedar desactualizados y remite a los canales oficiales para confirmar el procedimiento vigente.

## Verificaciones pendientes en producción

Este sandbox no tiene las variables públicas de Supabase, por lo que no pudo producir un listing real ni comprobar el HTML final de una publicación con datos reales. Antes de considerar Part 1 verificada en producción, el propietario debe ejecutar el deploy con esas variables y revisar el código fuente —no solo el DOM hidratado— de una URL `/listings/{id}` para confirmar que título, precio, descripción e imágenes aparecen como texto y tags reales sin JavaScript.

También debe validarse manualmente el JSON-LD de una publicación real con Schema.org o Google Rich Results Test, revisar una vista previa real de WhatsApp/Facebook y confirmar que una publicación nueva, editada, vendida o eliminada queda correctamente reflejada después del siguiente rebuild diario. Esta última parte no puede verificarse localmente sin acceso a la base y al deploy real.
